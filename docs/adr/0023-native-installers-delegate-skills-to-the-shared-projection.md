# Native installers delegate skills to the shared projection

Status: accepted

[ADR-0019](0019-shared-project-projection-with-host-adapters.md) made `.agents/skills` the Shared Project Projection, but `dhpk-install cursor|codex-sync` still write skills as real files into `.cursor/skills` and `.codex/skills`, using a separate install-profile selection. Two writers with two selections let the copies drift. We decided that native installers stop owning skill content: they select skills into the shared projection and give their Host a Host Binding to it, one skill at a time, owned by the Projection Receipt. ADR-0019 stays accepted and unchanged; this ADR refines how its Host Adapters are wired for skills.

## Decision

- **Skills only.** Agents, rules, commands, hooks, MCP, and policy stay in Native Projections, as ADR-0019 requires. dhpk does not manage consumer instruction files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) and creates no symlinks between them.
- **Per-skill bindings, never whole-directory links.** A Host Binding covers one skill and is recorded in `.agents/.dhpk-installed.json`. dhpk never replaces a Host's skill directory with a link such as `.cursor/skills -> ../.agents/skills`, because the user's own skills and foreign content must keep working next to dhpk's.
- **One selection.** `--profile X` selects the profile's resolved skill IDs in the shared projection, filtered to skills whose inventory lists that Host's surface. Each install profile's projection set is declared explicitly in the manifest, generated by `catalog.js` and checked in CI. It is never inferred at install time. When two Hosts install different profiles into one project, the shared projection holds the union of skills bound by any Host, and each Host is bound only to its own profile's selection.
- **Discovery is gated on Consumer Evidence.** A Host stops receiving native skill files only when its discovery consumer probe has a PASS record. Until then the installer falls back to per-skill bindings inside the native directory (the mechanism Claude already uses), and the plan says why.
- **Migration on `--update`.** Unchanged legacy receipt-owned native skill entries are removed and handed to the shared projection. Modified entries stay in place, are reported, and require `--adopt`. `--plan --json` shows how each entry will be handled.
- **Uninstall.** Removing a Host removes only its bindings and native assets. Shared content goes only when no other Host Binding still uses it, per ADR-0019.

## Considered Options

- **Whole-directory symlinks** (`.claude/skills`, `.cursor/skills`, `.agent/skills` → `../.agents/skills`), as proposed in #612. Rejected: they take over directories dhpk does not own, hide the user's native skills, and cannot be removed per Host.
- **Instruction-file topology** (`CLAUDE.md` / `GEMINI.md` → `AGENTS.md`). Rejected: those files belong to the consumer, and ADR-0019 scopes the shared projection to skills.
- **Assume every Host reads `.agents/skills`.** Rejected: static structure is not Consumer Evidence. A Host without a passing probe would silently lose its skills.

## Consequences

The native installers depend on the shared projection compiler and on a reliable Cursor consumer probe (#607). The unmet-dependency check from #609 must read the shared selection instead of the native one. Existing installs keep working until `--update`, and hand-edited skills are never overwritten without `--adopt`.
