# skill-directory-self-containment Specification

## Purpose

Define the canonical Skill directory as the relocatable runtime unit. The directory carries the procedures and bundled resources its supported workflows require. Shared copies, optional peer delegation, isolated verification, and publication stay inside that boundary. Host support and Consumer Evidence stay separate facts.

## Requirements

### Requirement: Every canonical Skill has a standard auditable structure

Every Skill selected from the canonical distribution inventory SHALL have a
regular `SKILL.md` with valid `name` and `description`. Supporting scripts,
references, assets, and Host metadata SHALL be included only when the workflow
needs them. Structural validation SHALL account for every inventory entry and
SHALL NOT require a command counterpart or a `scripts/` directory for an
instruction-only Skill.

#### Scenario: Instruction-only Skill is complete

- **WHEN** an inventory Skill has valid instructions and all required references
  but no executable helper
- **THEN** structural validation accepts it without requiring a placeholder
  script, command, or custom packaging descriptor

#### Scenario: Catalog coverage is incomplete

- **WHEN** the audit omits an inventory Skill or finds a required local resource
  missing
- **THEN** it fails with the stable Skill identity and missing coverage/resource
  rather than reporting the catalog as complete

### Requirement: The canonical Skill directory is the runtime resource boundary

A canonical Skill directory SHALL contain the required procedures, executable
code, configuration, schemas, templates, and transitive bundled resources for
its supported workflows. Given declared external tools and Host capabilities,
copying that directory SHALL require no dhpk source checkout, sibling Skill,
repository manifest, consumer build, or dhpk packaging step. Runtime code SHALL
resolve bundled resources relative to the Skill and task inputs relative to
their explicit consumer context; it SHALL NOT search ambient parent checkouts.

#### Scenario: A raw directory is relocated

- **WHEN** only the Skill directory is copied to an unrelated location and the
  workflow runs against a separate fixture project without source-root variables
- **THEN** its required local resources resolve and its observable behavior,
  arguments, exit status, and output contract remain correct

#### Scenario: An ambient checkout can hide a missing resource

- **WHEN** a required local resource is missing but a similarly named resource
  exists in a parent directory or sibling Skill
- **THEN** the workflow reports the missing resource and does not load that
  ambient substitute or report success

#### Scenario: Setup receives a distribution artifact

- **WHEN** a setup workflow is given an explicit artifact to install
- **THEN** the artifact is treated as task input while the Skill's required
  adapter implementation remains available within its own runtime boundary

### Requirement: Shared runtime copies are deterministic authoring outputs

Shared runtime resources SHALL have one maintained source and explicitly mapped
physical copies within consuming Skill directories. Required copies SHALL be
version-controlled with their callers and cover the complete bundled dependency
chain. Authoring synchronization SHALL preserve required executable modes and
produce identical outputs from identical inputs. Read-only checking SHALL
detect missing, stale, or orphaned managed copies without modifying files;
consumers SHALL NOT need to run the synchronizer.

REQ-3: Explicit copy mappings SHALL be declared in the consuming Skill
directory. The repository `manifests/skill-resources.json` SHALL be a generated
aggregate of those declarations; `manifests/skill-resource-copies.json` SHALL
remain the generated fingerprint ledger of copied bytes and modes. A
`--write` / `--check` pair SHALL keep the aggregate aligned with the
directories. Hand-editing the aggregate without a matching directory
declaration SHALL fail the check.

#### Scenario: Shared source changes without synchronized copies

- **WHEN** maintained shared content changes but a required Skill-local copy
  still contains the prior content
- **THEN** the check fails and identifies that copy while leaving all files
  unchanged

#### Scenario: Synchronization is repeated

- **WHEN** synchronization runs twice with identical sources and mappings
- **THEN** the generated bytes and required modes are identical, and neither
  run modifies unrelated files

#### Scenario: A mapping exists only in the aggregate manifest

- **WHEN** `manifests/skill-resources.json` lists a copy for a Skill that the
  Skill directory does not declare
- **THEN** the resource drift check fails with the Skill identity and leaves
  files unchanged

### Requirement: Resource synchronization and fingerprints fail closed

Resource mappings SHALL reject escaping paths, symlinked sources or destinations,
duplicate destinations, file/directory-prefix collisions, and required source
or destination components excluded by distribution ignore policy, including
`__pycache__` and `*.pyc`. The selected synchronization set SHALL be preflighted
before publication. Every copied runtime resource SHALL contribute to its
Skill's content fingerprint; invalid or changed staged content SHALL prevent
publication without altering previously accepted output.

#### Scenario: A required runtime asset uses an ignored destination

- **WHEN** a mapping declares `__pycache__/runner.js` or `scripts/runner.pyc`
- **THEN** validation rejects it before copying, even if the source exists and
  ordinary generated bytecode would otherwise be ignored

#### Scenario: A required runtime asset uses an ignored source

- **WHEN** a mapping reads a source beneath `__pycache__` or a `*.pyc` source
  into an otherwise ordinary destination
- **THEN** validation rejects the mapping before mutation

#### Scenario: Staged runtime bytes no longer match the verified source

- **WHEN** required runtime content changes between source validation and final
  staged verification
- **THEN** publication fails rather than accepting unverified bytes with an
  unchanged receipt fingerprint

### Requirement: Custom distribution metadata is not a Skill prerequisite

Canonical Skill directories SHALL contain no `skill-package.json` descriptors
after migration. Per-skill distribution and synchronization metadata SHALL be
authored in the canonical Skill directory as specified by
"Per-skill distribution metadata is directory-owned". An individual Skill's
core workflow SHALL NOT require `distribution.yaml` or distribution-owned
authoring fields at runtime. A bounded reader bundled locally with the Skill
MAY read handoff `metadata.dhpk-next` / `metadata.dhpk-modes`; existing
`metadata.dhpk-invocation-class` behavior SHALL remain valid. That runtime
reader SHALL NOT require repository manifests, import the CI parser, or load
peer procedure bodies. Handoff lookup and authority SHALL retain their
separate runtime behavior gate. Aggregate
`manifests/` files MAY hold generated per-skill projections and editorial
overlays; they SHALL NOT be the authoring source of per-skill facts. Readers,
generators, tests, and local resources SHALL migrate together. Runtime JSON
configuration and schemas used by the workflow SHALL remain valid bundled
resources.

#### Scenario: Skill executes without packaging metadata

- **WHEN** an isolated Skill has all required resources but no repository
  manifest or per-Skill packaging descriptor
- **THEN** its supported workflow remains usable with its declared external
  prerequisites

#### Scenario: Descriptor is removed before its resources are moved

- **WHEN** a former runtime-overlay declaration disappears while its required
  file is absent from the canonical Skill directory
- **THEN** completeness validation fails instead of treating descriptor removal
  as a successful migration

#### Scenario: Distribution authoring metadata is unused at runtime

- **WHEN** an isolated Skill includes `distribution.yaml` and distribution-owned
  metadata but is given no repository `manifests/` tree
- **THEN** its representative public task runs from bundled resources without
  opening `distribution.yaml` or distribution-owned authoring fields

#### Scenario: Bundled handoff reader uses permitted metadata

- **WHEN** relocated flow-guide resolves `dhpk-next` / `dhpk-modes` through its
  bounded locally bundled reader
- **THEN** lookup remains usable without repository manifests, CI-parser imports,
  or peer procedure bodies, preserves invocation-class behavior, and leaves
  execution authority and runtime behavior to the separate handoff gate

### Requirement: Script-path migration is a direct ownership-preserving cutover

Migrated exclusive legacy script paths SHALL be removed without compatibility
shims. Repository-owned callers, tests, installation mappings, and migration
guidance SHALL move to the new paths in the same migration batch. Existing
Claude command front doors, stable Skill identities, and approved invocation
authority SHALL remain intact. Edited, foreign, or unowned consumer files
SHALL be preserved and reported rather than overwritten or deleted.

#### Scenario: A migrated runner is installed

- **WHEN** the new version installs a migrated runner into a managed Skill
- **THEN** the new Skill-relative entry executes, the distribution contains no
  legacy script-path shim, and retained commands forward unchanged authority

#### Scenario: A consumer owns a modified legacy file

- **WHEN** migration encounters a modified or unowned file at an old destination
- **THEN** it preserves that file and reports the required manual action without
  marking migration complete for the conflicting entry

### Requirement: Peer-Skill delegation is optional without weakening gates

Each Skill SHALL provide its mandatory procedure and bundled resources without
requiring installation of another Skill. Peer delegation SHALL be optional and
SHALL preserve the same authority and evidence contract. Required independent
review roles, external tools, and Host capabilities SHALL remain explicit
prerequisites; their absence SHALL produce `BLOCKED` rather than skipped checks,
fabricated evidence, or self-review presented as independent verification.

#### Scenario: A peer Skill is not installed

- **WHEN** an otherwise supported workflow has its required capabilities but
  the optional peer Skill is absent
- **THEN** the local procedure remains usable and no hidden peer installation
  requirement is introduced

#### Scenario: Independent review is unavailable

- **WHEN** a workflow requires independent review and no permitted reviewer
  capability is available
- **THEN** the workflow reports `BLOCKED` and does not treat a local self-check
  or optional delegation fallback as approval

### Requirement: Self-containment does not expand Host support

Host-Bound Skills SHALL retain their declared Host and capability requirements.
Structural completeness, copying, and package generation SHALL NOT establish
new Host support or runtime availability. Unsupported Host actions SHALL produce
an explicit non-pass result with the unavailable capability identified.

#### Scenario: A complete Host-Bound Skill is used on an unsupported Host

- **WHEN** all local files exist but the requested Host-specific capability is
  unsupported in the current Host
- **THEN** the Skill reports `BLOCKED` or `UNAVAILABLE`, performs no guessed
  equivalent action, and makes no parity claim

### Requirement: Handoff creation rejects unsafe ancestors before writes

Resume/save helpers SHALL validate existing ancestor components even when the
requested handoff leaf does not exist. The write boundary SHALL independently
enforce safe destination creation instead of relying only on an earlier phase
detector result. A symlinked destination or ancestor SHALL fail before a handoff
or session-context file can be created outside the selected target.

#### Scenario: Missing handoff is below a symlinked directory

- **WHEN** the requested handoff is absent beneath a symlinked `.dhpk`, `.claude`,
  or explicitly selected parent directory
- **THEN** phase detection fails with a nonzero exit, does not report `save`,
  and leaves the external target untouched

#### Scenario: Destination changes after phase detection

- **WHEN** a previously safe destination becomes symlinked before Save writes
- **THEN** the write fails without creating or overwriting an external handoff

### Requirement: Completion evidence covers canonical Skills and consumers separately

REQ-6 continued: Verification SHALL include inventory-wide structure/resource
coverage and authoring fixture definitions for declared executable entries,
with appropriate reference/routing checks for instruction-only Skills.
Generated packages, installation migration, and actual Host probes SHALL have
separate evidence. Missing fixture definitions, failed checks, and unavailable
Host probes SHALL remain visible non-pass states. Routine CI SHALL classify packaged Skill-script files and execute recognized
public CLI entries through the operability smoke suite (exit code and output
shape). Internal modules SHALL retain their applicable existing behavior
coverage. Routine CI SHALL NOT present that smoke as representative isolated
runtime. Neither a help-only check nor successful packaging SHALL substitute
for representative runtime behavior. Representative isolated runtime remains a
publication or on-demand evidence class; daily CI MAY omit historical family
isolation suites when the smoke suite invokes those public CLI entries.

#### Scenario: Raw-directory behavior fails after package tests pass

- **WHEN** projection tests pass but an isolated canonical entry cannot resolve
  a required resource or violates its output contract
- **THEN** self-containment remains failed and overall migration is not complete

#### Scenario: A Host probe cannot run

- **WHEN** required Host tooling or credentials are unavailable for a consumer
  probe
- **THEN** the report records `NOT_RUN`, `BLOCKED`, or `UNAVAILABLE` and does not
  upgrade structural evidence into consumer runtime PASS

#### Scenario: Operability smoke is not representative runtime

- **WHEN** the Skill-script operability smoke passes using `--help` or a start
  fixture in an isolated empty project
- **THEN** reports SHALL NOT record representative isolated runtime as PASS
  from that smoke alone

### Requirement: Publication preserves selection and verified ownership

Publishers SHALL materialize complete physical Skill trees without injecting
missing runtime resources from outside the Skill at publication time. They SHALL
retain inventory/profile selection, command-owner inclusion, deterministic
fingerprints, and ownership-aware update/rollback. Malformed receipts SHALL
fail closed. Provenance-bound generation SHALL use an authorized clean source
revision; missing commit or publication authority SHALL remain an explicit gate.

#### Scenario: Required resource is absent during publication

- **WHEN** a Skill selected for publication lacks a required local runtime file
- **THEN** publication fails instead of silently supplementing it from a root
  script or neighboring Skill

#### Scenario: A historical managed installation is updated

- **WHEN** a valid historical receipt proves ownership of unchanged files
- **THEN** migration verifies and updates those files without reselecting the
  profile or changing stable identities, while preserving conflicting user files

#### Scenario: A receipt or source revision is not trustworthy

- **WHEN** ownership metadata is malformed or provenance generation lacks an
  authorized clean source revision
- **THEN** the operation is blocked without hand-editing receipts, fabricating
  provenance, or silently committing the worktree

### Requirement: Coverage fixture definitions remain until remapped

REQ-6: Inventory-wide skill-directory coverage SHALL continue to require a
fixture definition for every declared executable entry. Authoring registration
of those definitions SHALL remain valid after isolation-test deletion. Fixture
modules that the coverage validator still imports SHALL NOT be deleted as
orphans. Bridge, flow, resume, and skill-directory fixture helpers that other
KEEP suites or the coverage validator require SHALL remain. A later remap of
`fixture_ids` onto the operability smoke suite MAY retire family-specific
definition modules only after coverage validation still passes.

#### Scenario: Isolation tests are gone and coverage still validates

- **WHEN** family isolation test files are deleted and the coverage validator
  runs with the remaining fixture registrations
- **THEN** every declared executable entry still has a known fixture id and
  matching entry path, or coverage fails with the unknown fixture identity

### Requirement: Consolidated families include complete delivery resources

SCF-REQ-002: Each family in the closed self-contained consolidation mapping SHALL include every required local procedure, document, reference, script, template, configuration, and transitive resource within its installed family directory. All local paths SHALL resolve from that directory without reading a source checkout, sibling skill, retired predecessor, repository manifest, or ambient parent. Shared canonical sources and deterministic authoring-time copies SHALL remain permitted. Missing required assets SHALL fail build, installation, or delivery validation; they SHALL NOT be an ordinary user workflow branch or an instruction to obtain the omitted package resource. Runtime missing-resource protection SHALL fail closed before dependent mutation and SHALL NOT excuse incomplete delivery.

#### Scenario: Family survives relocation and predecessor deletion

- **WHEN** a complete family directory is copied to an unrelated temporary location, ambient source variables and module paths are cleared, and predecessor/sibling skills are absent
- **THEN** its representative supported task resolves all local resources and produces the expected output using only declared external capabilities and explicit task inputs

#### Scenario: Required package asset is removed

- **WHEN** a required local asset is deleted from a candidate family package while an ambient copy remains available
- **THEN** delivery validation fails with the family identity and missing resource instead of borrowing the ambient copy or requesting that the user supply the omitted asset

#### Scenario: Runtime detects tampering after delivery

- **WHEN** a required bundled resource becomes unavailable before a dependent mutating action
- **THEN** runtime protection returns a non-pass missing-resource result without performing that action or modifying the target

### Requirement: Consolidated family acceptance observes representative tasks

SCF-REQ-010: Every mapped successor family SHALL have representative public task fixtures covering selected resources/actions, observable output, required resource closure, scope/version clarification when relevant, and effect authority. Executable families SHALL be exercised in relocated directories with ambient dependencies removed; instruction-only branches SHALL have task-to-reference/output oracles beyond matching prose. Existing synthetic fixtures, static checks, and generated package success SHALL NOT substitute for family-specific behavior or actual Host runtime. External APIs MAY use bounded test substitutes, but reports SHALL identify the substitute and retain unavailable live evidence as `NOT_RUN`, `BLOCKED`, or `UNAVAILABLE`.

#### Scenario: Existing synthetic isolation tests pass

- **WHEN** synthetic isolation tests pass but a consolidated family has no representative public-task fixture
- **THEN** that family's behavioral acceptance remains incomplete rather than inheriting the synthetic result

#### Scenario: External service is simulated

- **WHEN** a family fixture uses a bounded substitute for an external API
- **THEN** the report records the tested contract and substitute separately from live service and Host evidence

#### Scenario: One family still reads a sibling

- **WHEN** aggregate packaging passes but one relocated family fails without its sibling directory
- **THEN** that family fails self-containment and overall consolidation acceptance remains non-pass

### Requirement: Per-skill distribution metadata is directory-owned

REQ-1: Each canonical Skill directory SHALL be the authoring source of its
per-skill distribution facts. Compact identity and front-door facts SHALL be
declared in official `SKILL.md` frontmatter keys and nested `metadata.dhpk-*`
keys. Bulk maps (resource copies, directory coverage, usage grammar, and
standalone dependency lists) SHALL be declared in a sibling `distribution.yaml`
in that directory. Top-level `SKILL.md` frontmatter SHALL use only the official
key whitelist; unofficial top-level keys SHALL fail skill validation. Adding,
removing, or merging a Skill for per-skill facts SHALL require edits only in
that Skill's directory. Editorial overlays (lifecycle, surfaces, marketplace
curation, install-profile membership) remain outside this requirement.

The sibling file is authoring metadata. It SHALL NOT be a runtime packaging
descriptor, SHALL NOT restore `skill-package.json`, and SHALL NOT be read by
the Skill's core workflow. Keys under `metadata` that this change introduces
SHALL use the `dhpk-` prefix and SHALL NOT occupy the `dhpk-handoff-*` range
reserved for `declare-skill-handoffs-in-frontmatter`. The nested parser and
closed allowlist SSOT SHALL be `scripts/ci/_lib/frontmatter.js`;
`validate-skills.js` SHALL consume it for schema validation and retain the
official top-level whitelist without a second nested allowlist. Existing
`dhpk-invocation-class` and actual handoff `dhpk-next` / `dhpk-modes` SHALL be
preserved.

#### Scenario: A new Skill is added with default classification

- **WHEN** a contributor adds a complete canonical Skill directory including
  `SKILL.md` and, when bulk maps exist, `distribution.yaml`, and does not edit
  other Skill directories
- **THEN** per-skill generation produces that Skill's inventory, coverage,
  resource, usage, and command rows from that directory alone

#### Scenario: An unofficial top-level frontmatter key is introduced

- **WHEN** a Skill `SKILL.md` declares a top-level frontmatter key outside the
  official whitelist
- **THEN** skill validation fails and names the file and unknown key

#### Scenario: Bulk maps are stored only in a central manifest

- **WHEN** resource-copy or coverage facts for a Skill exist in `manifests/`
  but are absent from that Skill's `distribution.yaml`
- **THEN** the directory-owned drift check fails with the Skill identity and
  missing declaration
