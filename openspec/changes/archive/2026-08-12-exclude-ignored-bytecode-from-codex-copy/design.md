## Context

`scripts/hooks/install-codex-skills.sh` embeds the Codex materializer in
Python. `hash_path()` currently hashes every directory entry, while both normal
and atomic copy paths call unfiltered `shutil.copytree(..., symlinks=False)`.
Because Python execution creates ignored `__pycache__` and `*.pyc` files under
skills, copy mode currently ships host-generated bytecode and changes the
schema-v3 source fingerprint (#157).

The installer is consumed directly by users and by the release consumer gate;
its existing receipt, ownership, collision, migration, and rollback contracts
must remain unchanged for distributable content.

## Goals / Non-Goals

**Goals:**

- Define one path filter for distributable Codex content.
- Apply it consistently to directory hashing, source enumeration, normal copy,
  atomic copy, and the release consumer-gate fingerprint used to validate a
  clean project projection.
- Keep ignored bytecode out of materialized projects and fingerprints.
- Prove behavior through the public installer command and existing fixture
  conventions.

**Non-Goals:**

- No receipt schema version bump or new installer flag.
- No change to symlink mode's link target semantics.
- No exclusion of ordinary Python source, Markdown, TOML, or other non-bytecode
  files.
- No changes to the native package generators, which already filter these
  entries.

## Decisions

### 1. Filter by path component and filename

The filter will reject a directory entry named exactly `__pycache__` and a file
whose basename ends with `.pyc`. It will be used as a shared `copytree` ignore
callback and as the traversal predicate for `hash_path()`. This makes source
fingerprints describe the same tree that copy mode materializes. Filtering only
the copy operation is rejected because it would leave receipt fingerprints
unstable; filtering only hashes is rejected because bytecode would still ship.

### 2. Retain directory names in the filtered hash shape only when included

Excluded entries contribute neither their name nor a child digest. Included
directories and files retain the current deterministic SHA-256 framing, so
existing fingerprints change only where ignored content had previously leaked
into the digest.

### 3. Test through a copied fake plugin

The regression fixture will copy the repository's Codex tree into a temporary
plugin with dereferenced symlinks, inject ignored bytecode into a Python-backed
skill, invoke `install-codex-skills.sh --copy --force`, and inspect the receipt
and destination. It will then change ignored bytecode and re-run with
`--update`; the fingerprint and projection must remain unchanged while ordinary
source behavior remains covered by existing tests.

### 4. Keep the release consumer gate on the same evidence contract

`scripts/release/consumer-gate.js` fingerprints the project-local projection
independently from the embedded installer. Its traversal intentionally hashes
complete destination integrity, including any legacy `__pycache__` and `.pyc`
entries, so a pre-remediation receipt cannot hide stale or changed executable
bytecode. Source fingerprints and both copytree paths remain filtered; after
ownership is proven, update/migration replaces the destination with that clean
filtered projection.

## Risks / Trade-offs

- [Risk] A future distributable file may be intentionally named `.pyc` →
  [Mitigation] the package contract treats Python bytecode as non-portable;
  source `.py` remains included and any exception requires a separately
  specified distribution change.
- [Risk] Hash and copy filters diverge again → [Mitigation] the regression
  fixture asserts both omission and fingerprint stability through the public
  installer path.
- [Risk] Atomic staging could apply a different ignore callback → [Mitigation]
  wire the same helper into normal and atomic `copytree` calls and retain
  existing update/collision tests.

## Migration Plan

No receipt migration is needed. On the next `--update`, projections that contain
old bytecode will be reconciled against the filtered source; unchanged managed
entries follow existing ownership rules. A clean reinstall or `--uninstall`
remains the documented rollback path.

## Open Questions

None. The issue identifies the exact ignored patterns and the source/test
consumer boundary.
